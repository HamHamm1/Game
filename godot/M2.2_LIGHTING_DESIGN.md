# M2.2 — Time-of-Day & Lighting — Design & Implementation Reference

> **Canonical implementation reference for M2.2.** Approved 2026-09-05.
> Scope: time-of-day + lighting only. **M2.3 (weather) is a separate future
> milestone — not in this document's scope.** No weather, no rain/steam
> particles, no new environment art, no final materials, no NPCs/cooking/
> dialogue. Reconciles to the *actual* code (a single global environment),
> not the older "one controller per region" wording in ARCHITECTURE.md §10.

---

## 0. Creative intent (from the locked M2.0 direction)

The goal is not "the player can see" — it is **"the player wants to be
there."** Lighting must read as **natural light in a real Japanese rural
village**, never a gamey filter.

- **Evening (hero):** warm, nostalgic, beautiful, peaceful, cinematic —
  *"I want to live here."*
- **Interior:** warm, lived-in, comfortable, inviting.
- **Night:** peaceful, quiet, beautiful, dreamlike — **but comfortably
  navigable.** Night ≠ darkness.

**Avoid:** obvious color filters, strong screen tint, horror grading,
exaggerated blue night, exaggerated orange evening, artificial per-location
filters. Category differences give locations *character*, not different
color grading.

Automated tests prove correctness/invariants only. **Beauty, atmosphere,
and comfort can only be confirmed by the developer's on-device Android
test.**

## 1. Existing code this builds on (unchanged)

- **`TimeManager`** (autoload): `minutes_into_day` (0–1439), `day_index`,
  `real_seconds_per_game_minute = 1.0`. Enum `TimeBlock {NIGHT_EARLY,
  MORNING, AFTERNOON, EVENING, NIGHT_LATE}`. Emits `minute_passed(day,min)`
  (~1 Hz), `time_block_changed(old,new)`, `day_started(day)`. Savable
  (`"time"`). **Not modified by M2.2.**
- **`WorldEvents`** (autoload): pure signal bus. M2.2 subscribes to
  `minute_passed`, `location_entered(path)`, `location_exited()`,
  `region_loaded(path)`, `game_loaded()`. **No new signals required.**
- **`world_root.gd`**: owns **one** `WorldEnvironment` (`_environment`) and
  **one** `DirectionalLight3D` (`_sun`), built in `_setup_environment()`.
  `_apply_graphics()` writes the GraphicsManager preset params to them.
- **`GraphicsManager`** (autoload): LOW/MEDIUM/HIGH/ULTRA presets; owns the
  cost knobs (shadows, fog on/off + density, glow, ssao, scale_3d, msaa,
  view_distance). Emits `changed`.
- **Loaders**: `RegionLoader.active()` / `LocationLoader.active()` expose the
  live scene root; interiors load at a large spatial OFFSET and the player
  teleports in/out (so entering/exiting is already a visual cut).

## 2. Architecture implemented by M2.2

A single **`RegionLightingController`** — a plain `Node`, created by
`world_root` and handed references to `_sun`, `_environment`, and the two
loaders. **Not an autoload** (keeps `project.godot` untouched; guarantees
valid scene refs; lifecycle = the world's).

```
world_root
 ├── WorldEnvironment (_environment)   ── owned by world_root
 ├── Sun (DirectionalLight3D, _sun)    ── owned by world_root
 ├── RegionLightingController (NEW)     ── setup(_sun,_environment,region_loader,location_loader)
 │      subscribes: minute_passed, location_entered/exited, region_loaded, game_loaded
 │      writes ONLY the mood props (see §7 ownership table)
 └── RegionLoader / LocationLoader / Player / HUD / PauseMenu ...
```

**Resolved look** =
`base(time-of-day, interior?) × category-modifier × mystery-modifier`,
then a **readability clamp**. Interior vs exterior is decided by
context (`location_entered`/`location_exited`), *not* by a global ambient
raise — see §5.

**Reconciliation:** ARCHITECTURE.md §10 says "one controller per region";
the code has one global environment, so M2.2 uses **one** controller that
re-reads the active scene's category on `region_loaded` / `location_entered`.
(§10 wording to be updated when convenient — noted, not blocking.)

## 3. Continuous time-of-day model (`LightingProfile`)

Lighting is a **continuous function of `minutes_into_day`**, sampled from a
small sorted keyframe table and linearly interpolated (with midnight
wraparound). This makes Morning→Day→Evening→Night→Morning inherently smooth
— there is no per-block "switch." The 5 TimeManager blocks map to the four
canonical states: `MORNING→Morning`, `AFTERNOON→Day`, `EVENING→Evening`,
`NIGHT_EARLY+NIGHT_LATE→Night`.

`LightingProfile` is a typed value object (no raw `Dictionary` in gameplay,
DESIGN principle 7) holding only **mood** properties:
`sun_pitch_deg`, `sun_yaw_deg`, `sun_energy`, `sun_color`,
`ambient_color`, `ambient_energy`, `bg_color`, `fog_color`.

Exterior keyframes (restrained, natural — tunable constants in
`lighting_profile.gd`), by minute of day:

| ~time | state | character |
|---|---|---|
| 02:30 | deep night | cool, low moon fill, ambient at floor — still navigable |
| 05:30 | first light | soft cool→warm dawn |
| 07:00 | morning | fresh, cool-neutral, gentle shadows |
| 12:00 | day | neutral-bright, readable, good visibility |
| 17:00 | late afternoon | warming, longer shadows |
| 18:30 | **evening (hero)** | golden, warm directional, long shadows, warm/cool contrast |
| 20:15 | dusk | dimming warm→cool |
| 22:30 | night | cool moonlight, warm-window-ready, ambient at floor |

**Night is never black:** exterior ambient is clamped to a readability
floor and the sun is kept as a low, non-zero moonlight fill.

---

## 4. Exterior readability

Handled by the exterior keyframes + the exterior readability floor
(`EXTERIOR_MIN_AMBIENT`). Guarantees readable paths, terrain, vegetation,
and architecture at *every* time, most critically at night — without making
the day look flat. Restrained values (no exaggerated blue night).

---

## 5. Interior readability & warm baseline (separate context)

**Interior darkness is NOT solved by raising global exterior ambient.**
Interior is a **separate context** selected only while a location is loaded:

- Warm ambient with its own, higher floor (`INTERIOR_MIN_AMBIENT`) →
  always warm, inviting, readable.
- Subtly modulated by the exterior time of day (a little cooler/brighter by
  day, warmer/cozier at night) so interiors feel **connected to windows and
  the outside** — but never dark.
- The sun is demoted to a soft warm fill (the ceiling occludes it anyway).
- **Zero extra dynamic lights** for the baseline (all via the Environment).
  Optional practical/emissive lanterns & windows are **M2.4** scene/material
  work, explicitly not in M2.2.

Because the interior profile is applied *only during interior context*, it
never brightens the outdoor world. This is the key correction from M2.1.

## 6. Location categories & the mystery modifier

**Categories** are subtle, data-driven **tags → small modifiers**, applied
on top of whichever base (exterior or interior). They give locations
*character*, not different color grading. Full set implemented now:

`residential`, `commercial`, `natural`, `water`, `landmark`, `threshold`,
`interior`.

- Each maps to a **restrained** delta (small warmth bias and/or ≤ ~5%
  ambient-energy nudge, tiny fog-tint bias). No category is a separate
  visual filter.
- The tag lives on the scene root as `@export var lighting_category:
  StringName`; the controller reads it from the active region/location node.
  Absent → neutral default.
- Interior-ness is driven by **context** (the location signals), not by the
  `interior` tag; the tag is available for completeness/override.

**Mystery is NOT a category.** It is a separate, sparse **local modifier**
(`lighting_mystery: float` 0..1 on a specific scene) layered on top of the
normal beautiful lighting: a small cool shift, a small ambient reduction
(still clamped above the floor), a slight cool fog raise. **No red, no
horror grading, no map-wide darkening.** Used rarely (e.g. one unusually
quiet spot). Default 0 everywhere.

Category assignments for the current blockout:

| Scene | category |
|---|---|
| `blockout_town` (region) | `residential` |
| `blockout_interior` (player home / phase-1 test) | `residential` |
| `restaurant_interior` | `commercial` |
| `shop_interior` | `commercial` |
| `workshop_interior` | `commercial` |
| `bathhouse_interior` | `landmark` |

## 7. Graphics-preset interaction (strict, non-overlapping ownership)

The controller writes **only** mood props; it never re-enables a feature a
preset disabled. LOW stays LOW.

| Property | Owner |
|---|---|
| `shadow_enabled`, `directional_shadow_max_distance` | GraphicsManager |
| `fog_enabled`, `fog_density` | GraphicsManager |
| `glow_enabled`, `ssao_enabled` | GraphicsManager |
| `scaling_3d_scale`, `msaa_3d`, `camera.far` | GraphicsManager |
| `_sun.rotation`, `_sun.light_energy`, `_sun.light_color` | **LightingController** |
| `_environment.ambient_light_color` / `ambient_light_energy` | **LightingController** |
| `_environment.background_color`, `fog_light_color` (tint only) | **LightingController** |

No property is written by both → order-independent, no fights. Warmth/glow
feel comes from **light color + energy**, never from toggling `glow_enabled`
(so LOW, with glow off, still looks right). An automated test asserts the
controller leaves every GraphicsManager-owned property untouched.

---

## 8. Transitions

- **Day cycle:** continuous — re-applied on `minute_passed` (~1 Hz);
  per-minute steps are imperceptible. **No `_process`, no per-frame cost.**
- **Context switches (enter/exit building):** an immediate snap. This is
  masked by the existing scene load + player teleport (already a visual
  cut), so no crossfade is needed — keeps the implementation small.
- On `game_loaded` / `region_loaded` / `location_*`: re-resolve and apply
  immediately.

---

## 9. Save / load

Lighting is a **pure function of `TimeManager` (already saved) + current
context (transient)**. **No lighting state is saved; `SaveManager` is not
modified.** On `game_loaded` the controller re-applies for the restored
minute.

---

## 10. Android performance

- One directional light (existing sun); **no new dynamic lights.**
- Lighting = a handful of property writes ~1×/sec, event-driven.
- No real-time GI, no added post, no volumetric fog. Fog stays the cheap
  Environment fog GraphicsManager already configures; the controller only
  **tints** its color.
- **Baked vs dynamic:** M2.2 (blockout) is all the single dynamic sun +
  Environment ambient — **no lightmaps** (geometry is primitive and will
  change). LightmapGI bakes + emissive lanterns/windows + a few accent
  lights are **deferred to M2.4** once geometry stabilizes.

## 13. On-device acceptance tests (developer, Android — the real gate)

1. Morning/Day/Evening/Night each look distinct and **beautiful**.
2. **Evening reads as the golden-hour hero** state.
3. **Night is comfortably navigable** outdoors (not dark).
4. **Interiors are warm and readable** in all four blocks (M2.1 fix).
5. Day cycle transitions are smooth; enter/exit building has no jarring
   flash beyond the normal scene cut.
6. **LOW preset:** still readable; no shadow/fog/glow LOW disables; FPS
   unchanged vs M2.1.
7. HIGH/ULTRA: shadows/glow present, lighting still balanced.
8. Save at night → load → still night, correct look.
9. Full day loop wraps Night→Morning cleanly.
10. Lighting reads as *natural light*, not a filter; no exaggerated blue/
    orange; no horror feel.

## 14. Risks & fallback

- Interiors still dark on a real panel → raise the single
  `INTERIOR_MIN_AMBIENT` / interior energy constant; re-test.
- Night too dark/bright → adjust the one night floor constant.
- Banding on gradients → accept flat BG; glow off on LOW; dither later.
- Lighting vs preset collision → strict ownership table (§7) + test.
- Mystery drifting toward horror → tiny deltas, sparse flags, review vs
  M0 canon.
- The whole system is **additive and reversible** — disabling the
  controller degrades to a static environment (DESIGN principle 6).
